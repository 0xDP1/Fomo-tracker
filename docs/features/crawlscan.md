# CrawlScan on demand (through the Worker)

**Status:** approved 2026-10-14.

**Problem.** CrawlScan (crawlscan.fun) scores a coin 0–100 from who really operates the top wallets and what their exit would do to the price (35), virgin wallets (25), supply received by transfer instead of bought (20), snipers (10) and concentration (10), with a CLEAN / OK / RISKY / DANGER band and a one-line headline. The app's own Analyze top wallets block does three of those parts over 15 wallets and spends Helius credits; CrawlScan covers the whole holder set. Their site talks to an open, keyless API (`POST /api/scan`, `GET /api/result`) that doesn't allow calls from another website, so the Discord feed Worker forwards it (the same way it forwards GMGN). A **Run CrawlScan** button on the Check tab (Solana coins) and a **CrawlScan** button on each Call queue row start one scan; the Worker waits for the result (about 10 seconds), remembers it for 30 minutes per coin (in memory and in storage), and returns the score, band, five parts, headline, reason and the five biggest operators (wallets, share of float and supply, holding or sold). The Check tab shows it as a block like their page; the queue row gets a `CS 59 · RISKY` tag that opens the block from memory. The result also feeds the rug check: DANGER is a high finding, RISKY medium, CLEAN a good note, and CrawlScan's dump impact speaks for the operator finding when it is the larger estimate. On demand only, never in the automatic queue checks: each scan runs on their servers. No new dependencies, no key. If their API changes or is paused the block says so and the app's own blocks still work. We know it works when unit tests boil a recorded real answer down to the summary and raise the right findings, a Worker test runs the start / wait / cache flow against a fake crawlscan.fun (including the paused case and the key check), a browser test runs both buttons and shows the block, the tag, the bars and the finding, and a live scan on the Check tab matches crawlscan.fun's page for the same coin.

## Rules

- Logic in `crawlscan.js` (shared by the app and the Worker, like `calls.js`): `summarize`, `startOutcome`, `facts`, `fresh`, `label`, `isSolana`. UI in `crawl-ui.js`; the Worker route `/crawl?ca=` in `worker/index.mjs` (`crawl`), bundled by `node worker/bundle.js`.
- The Worker waits up to 25 s for a result, then answers `202 { pending: true }` and the app asks again (up to 3 times); the job id is kept 2 minutes so the wait resumes instead of starting another scan. `fresh=1` forces a new scan (the Refresh button).
- `paused` (crawlscan.fun answers "SOON": Solana scans switched off) shows as "CrawlScan has Solana scans paused right now".
- Findings: `csBand` DANGER → high `crawlscan`, RISKY → medium, CLEAN → good note; `csImpact` replaces `operatorDrop` in the operator finding when larger.
- The queue row keeps `{ score, band, impact, at }`; the Call score is unchanged by it (first).
- Credit: approach and data, CrawlScan (crawlscan.fun); every block links to their page for the coin.
