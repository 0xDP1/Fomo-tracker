# Move alerts from the price-move channel

**Status:** approved 2026-10-16 (owner: "For moving notifications can we just use this channel that's called price move bc it's more accurate").

**Problem.** The 2× and 4× alerts came from the Worker pricing calls every 5 minutes and the app pricing them while open, which lags and sometimes disagrees with what the server posts. Vision Scan's **price move** channel posts the coin the moment it crosses a tier (PM-1 2×, PM-2 3×, PM-3 5×, PM-4 10× from the first scan) with the current FDV, a line `ATH: 1.9x. Now: 3.9x`, and the "Last mentions" list with the first call's market cap and caller. When the Worker reads a new message from the channel labelled "price move" in `CHANNEL_ID` (the same channel it already reads as a call source), it parses the multiple (the `Now` line, else current FDV over the first call's market cap, one decimal), the ATH multiple and the first caller, sends the Telegram alert straight away (`🚀 REELS 3.9× since the call ($88.2k → $351.0k) · valor456564 in PTN, called 2h ago · ATH 1.9×`, one per message), and folds it into the alert track with the server's figures: the base is the first call's market cap, the peak and last at least the posted FDV, 2× and 4× marked done so the Worker's own pricing alerts stay quiet on that coin, and `server: { x, ath, at, messageId }` kept on the record. The app folds the track on every feed read as before (`Recent.mergeRemote`), so Recent calls show the same multiple; a server alert the device has not shown yet pops the in-app banner (`REELS 3.9× since the call (price move)`), once per message. The move and volume alerts (the 5-minute pace rules) stay as they are. The first read of the channel (the backlog) never alerts. No new dependency, no new secret: the channel is matched by its label. We know it works from unit tests (the multiple, ATH, first call and caller parsed from the fixture message; FDV ÷ first call when the `Now` line is missing; another channel's message ignored; the Telegram text; the track update and the once-per-message rule) and a Worker test (a feed read with a new price-move message sends one Telegram message, the app's read carries the server alert, the same message again sends nothing).

## Rules

- Logic in `worker/alerts-core.js` (`isMoveChannel`, `priceMove`, `moveMessage`, `applyMove`), using `Calls.parseAlert`; the Worker's `poll` collects moves from new messages of move channels and `moveAlerts` sends and stores them. The channel label must contain "price move" (`1507…:price move`); the id stays in Cloudflare.
- `track[address].server` marks a coin the channel covers; `Recent.mergeRemote` copies a newer `server` from the Worker; `recent-ui.js` shows the banner for a `server` whose `messageId` is not in the device's `callServerShown` list (kept to the last 50).
- Storage: a move marks the store dirty like any new call; `AlertsCore.changed` counts the server message id.
- Without `TG_BOT_TOKEN` the track still updates (the app shows the alert); only the Telegram message is skipped.
